# agora_workflow

把 **语聚AI（集简云）聚合对话** 的消息推送落地成一个可看、可查、可自动化的会话工作台。

语聚汇聚了抖音企业号、企微代运营、微信公众号、微信客服、小红书私信/评论、钉钉、
快手、飞书、QQ、视频号等渠道的私信与评论。本程序订阅它的「聚合对话有新消息」
webhook，把各渠道报文归一化后入库，并提供实时会话界面与工作流引擎。

**零第三方依赖**，纯 Python 3 标准库。有 `python3` 就能跑。

```
语聚(集简云)
   │  POST  webhook
   ▼
app.py  ──jjy.py 归一化──▶  SQLite(store.py)  ──SSE──▶  会话工作台(index.html)
   │                                            └────▶  管理后台(admin.html)
   └──▶ 工作流引擎(workflow.py)  条件匹配 → 回复 / 调接口
```

## 快速开始

```bash
cp config.example.json config.json
```

编辑 `config.json`，至少填两项：

```jsonc
"jjy": {
  "enabled": true,
  "allow_company": ["你的公司ID"],   // 语聚控制台里能看到
  "bot_name": "你的机器人昵称",       // 群聊 @我 判定用
  "api_key": ""                     // 要发消息才需要，见下面「发送」一节
}
```

```bash
python3 app.py
```

打开 `http://127.0.0.1:9000/`（管理后台在 `/admin`）。

配置也可以在**管理后台 → 系统设置**里改，保存即写回 `config.json`。
大部分字段实时生效；标了「改动需重启」的（监听地址/端口、存储上限、去重窗口）
需要重启进程。


然后在语聚后台把回调地址填成 `http(s)://你的地址/gw/jjy-hook`，订阅「当聚合对话有新消息时」。

## 关于语聚的官方文档

**官方 OpenAPI 文档和实际推送对不上**，照文档写解析代码会全部取空。
实测差异（`jjy.py` 里按实际报文实现，并对两种形态都做了兼容）：

| 文档 | 实际推送 |
|---|---|
| `data.chat` / `data.message` / `data.user` / `data.source` | **`data.push_data.*`**，中间多一层 |
| `user_type` 枚举 1–6 | 实际出现 **7**（企微内部成员） |
| `source` 无 `rule_id` | 有，且类型不稳定：`"1557"` 和 `1557` 都出现过 |
| `source_account_id` 标 required | 实际是 `null` |
| `message_trigger_type: 1` = "API" | 实际 `message_trigger_name` 是「AI智能体回复」 |
| `message_type` 枚举跳过了 8 | **8 = 文件消息**，文档里根本没有这个号 |

**`message_content.text` 有时是一段 JSON 字符串，要再解一层**（文档只说是 text）。
不解的话，界面上那条消息显示的就是这一整串 JSON 原文：

```jsonc
// type 8 文件
{"text": "{\"fileUrl\":\"https://...\",\"name\":\"a.log\",\"size\":1036562}"}
// type 12 合并转发的聊天记录
{"text": "{\"chatHistoryList\":[...],\"title\":\"A和B的聊天记录\"}"}
// 引用回复 —— 任何类型都可能, 实测 type 2 就有
{"text": "{\"text\":\"开启了吧？\",\"quote_message\":{\"quote_message_id\":\"...\",
           \"sender\":\"刘雨欣\",\"content\":\"...\",\"quote_message_type\":\"text\"}}"}
```

8/12 按类型确定；引用**按有没有 `quote_message` 判定** —— 不能见到 type 2 的 text
以 `{` 开头就解，用户真发一段 JSON 文本会被拆掉。

**报文里有两个 `message_id`，别混：**

| 位置 | 形态 | 用途 |
|---|---|---|
| `message.message_id` | `api_<uuid>i` | 本程序的 `msg_id`。**去重、撤回、引用全用它** |
| `message_content.message_id` | 32 位 hex | 只在报文里出现，本程序不用 |

⚠️ 收到的引用块里 `quote_message_id` 是 **32 位 hex**（和内层那个同款），
很容易让人以为发送时的 `quoteMessageId` 也该填内层的 —— **不是**。
A/B 实测过：同一条消息分别用两个 id 发引用，只有**外层** id 客户端才显示成引用，
内层的发出去就是条普通消息。收和发这两个字段名字像，但不是一个 id 空间。

**还有一个文档里没有的事件类型：`chat_finish`**（对话结束），和 `ai_assistant_receives_msg`
走同一个回调地址。本程序按 `event_type` 区分，计入 `ignored` 而不是当成解析失败。

另外两个实测结论：

- **`message_create_time` 是毫秒**，不是秒。
- **incoming / outgoing 可配对**：同一轮问答的 `message_id` 是同一个 UUID，
  incoming 那条末尾多一个 `i`。去掉后缀即可关联提问与回复。

## 几个必须知道的坑

**① 回环。** 语聚会把机器人自己的回复**原样推回来**（`message_forward_type: "outgoing"`），
**包括本程序自己用 OpenAPI 发出去的那些**（`message_trigger_name: "API请求"`）。
存库要存（不然对话不完整），但绝不能拿它触发工作流，否则自问自答无限循环。
本程序把 outgoing 标成 `is_self_msg=1`，`on_message()` 见到就只入库不触发。

**② 这个 webhook 没有签名。** 官方 spec 里 `security: []`，没有任何签名或 token。
`jjy.allow_company` 白名单是**唯一**的身份校验：

- 公网部署**必须**配置 `allow_company`
- 回调路径本身建议带一段随机串（靠反向代理转发到 `/gw/jjy-hook`）
- 校验失败一律回 `200` 而不是 `403` —— 不给扫描者任何"这里有东西"的反馈

**③ 必须立刻返回 200。** 语聚等不到响应就会重推。本程序在 HTTP 线程里只做
白名单校验 + `event_id` 去重 + 入队，重活全在 worker 线程，不会因为处理慢而收到重复消息。

**④ 媒体默认不下载。** 语聚给的图片/文件是**公开的 S3 对象**——不带签名参数、
无鉴权直接 200，实测不会过期。所以默认 `media.mode = "link"`：不落盘，
`/media/<id>` 用 302 跳到原始 URL，前端 `<img src="media/xxx">` 照常出图。

省掉了下载线程、磁盘占用和失败重试。想留档（比如担心对方删文件）就改成
`"mode": "download"`，同一个 `/media/<id>` 会改吐本地文件，前端无感知。

用 302 而不是 301，就是为了让这个切换能反悔——301 会被浏览器永久缓存。

## 发送消息

出站走语聚的 `POST /v1/openapi/aggregate/message/send`。填上 apiKey 就能用：

```jsonc
"jjy": {
  "api_key": "G-xxxxxxxx",   // 语聚「应用助手 → 集成配置」页获取
  "send_qps": 1,             // 全局发送速率
  "send_retry": 2
}
```

管理后台 →「系统设置 → 接口凭证」也能填，旁边的 **校验 apiKey** 打的是官方的
`GET /v1/openapi/check`（注意这个接口**不守** `Code/Data/Msg` 那套约定，
直接回 `{"success": true}` 或 401）。

**⚠️ 填上之后工作台就是可写的**：手动发消息会真的发到客户那边，工作流的
「自定义回复 / 接口回复」动作也一样。如果语聚后台已经配了 AI 自动回复规则，
**同一条消息会有两个机器人抢答** —— 开之前先去语聚把规则确认一遍。

几个实现上的取舍：

- **接口的响应字段是大写开头的**：`{"Code": 2000, "Data": ..., "Msg": ...}`，
  不是常见的 `code/data/msg`。成功是 `Code == 2000`。
- **`Code=4000` 不重试**（参数错、会话已关闭，重试还是一样的结果）；
  只有 **429 / 5xx / 网络错误**才退避重试。401/402 直接翻译成人话返回。
- **全局串行限流**。语聚 429 的文案是 "Too Many Requests in one second"，
  限的是每秒。工作流命中一批消息时会连着发，不限流必撞 429。
- **apiKey 走 query string**（官方就这么设计的），所以代码里任何日志都不打完整 URL，
  `GET /gw/config` 返回给前端时也打码成 `********`；前端原样回传这个占位符
  就表示"不修改"。
- 发出去的消息**不在发送处入库** —— 语聚会把它回推回来，等回声那条，详见下面
  「自己发的消息也走回声入库」。

发别的类型直接调底层函数，`message_content` 原样透传：

```python
jjy_send(sid, 9, {"url": "https://.../a.png"})   # 9=图片 8=文件 3=语音
```

图片/文件要的是**公网可访问的直链** —— 本项目的 `/media/<id>` 在反代鉴权后面，
不能直接给语聚，要用 `STORE.get_media_cdn(mid)["url"]` 取语聚原始那个。

### 引用 / 撤回

工作台里鼠标悬停在**对方发的**气泡上会出现操作条，只有一个「引用」。
自己发的那侧没有操作条，撤回按钮整个没了 —— 原因都在下面。

- **引用** —— 发送时带上 `quoteMessageId`（填 `msg_id`，即上表里**外层**那个）。
  ⚠️ 只有企微代运营渠道支持，其他渠道语聚静默忽略，不报错也不生效。
  **收到的引用回复会画出引用块** —— 报文里带 `quote_message`（发送人 + 被引用正文），
  见 `jjy.py`。被引用的是图片/文件时 `content` 为空，前端出 `[图片]` 这类占位。

  > **A/B 实测（2026-08-11，企微代运营私聊）**，三种 id 打同一个接口，
  > `Code` 全是 2000，但客户端只有第一种画出引用块：
  >
  > | 引用目标 | 填的 id | 客户端 |
  > |---|---|---|
  > | 对方发的(incoming) | 外层 `api_<uuid>i` | ✅ 有引用块 |
  > | 对方发的(incoming) | 内层 32 位 hex | ❌ 静默无效 |
  > | 自己发的(outgoing) | 外层 `api_<uuid>`（无 `i`） | ❌ 静默无效 |
  >
  > 所以**只能引用别人发的消息**，工作台里自己那侧不给引用按钮 —— `Code:2000`
  > 骗不了人，给了就是点一下什么也不发生。AI 回复的「群里引用原消息」填的是
  > 提问那条的外层 id，走的是第一行，没问题。
- **撤回** —— `POST /v1/openapi/aggregate/message/revoke`。**前端按钮已经拿掉**，
  接口和后端(`jjy_revoke` / `POST /gw/revoke` / SSE `revoke` 事件)都留着。

  > ⚠️ **企微代运营渠道用不了。** 直接 curl 打接口实测（2026-08-11），拿刚回声
  > 回来的真 `message_id`、秒级时限内，返回
  > `{"Code":4000,"Data":"不支持撤回!","Msg":"不支持撤回!"}`。
  > 官方文档写的「支持小红书和企业微信」里的"企业微信"指的不是代运营这条链路。
  > 换 id、换参数都绕不过去，是渠道本身没这个能力，所以按钮点了必失败 ——
  > 与其每次点完才看见报错，不如不给。
  >
  > 将来接了小红书那类支持撤回的渠道，把 `index.html` 里 `ops` 那行的撤回
  > 按钮加回去就行（`me` 侧才给），后端一行都不用动。

### 自己发的消息也走回声入库

`message_id` **只有 webhook 推送里有** —— 发送接口的响应里没有（只有
`{channel, chat_id}`）。好在语聚现在会把 OpenAPI 发出去的消息回推回来：

```jsonc
"message_trigger_type": 1, "message_trigger_name": "API请求",
"message_forward_type": "outgoing", "user_type": 6,
"message_id": "api_49c00f65-dc37-4806-a40f-8a60bf95b347"   // 真 id
```

所以**发送处一行都不写库**，等回声。入库、SSE 广播、前端替换乐观气泡全走
`store_message()` 那一条路，同一句回复只会有一条，而且拿到的是真 `message_id`
—— 自己发的消息也能引用和撤回了。

> **早先不是这样。** 那时实测发两条 `sent` +2 而 `received` 一直是 **0**
> （同期别的推送照常进来，排除了网络/nginx/白名单），只能在发送成功后
> **本地补录一条**，`msg_id` 挂 `local:` 前缀的占位。上游行为变了之后补录就成了
> 第二条 —— 工作台里同一句回复显示两遍，所以补录整块删掉了。
> `local:` 开头的老消息前端仍然不给操作条：没有真 id，按钮点下去必然失败。

回声照样是 `outgoing` → `is_self_msg=1`，`on_message()` 只入库不触发工作流，
回环防线没变（见上面「① 回环」）。语聚**自己的 AI 规则**发的回复走的是同一条路。

### 抓取原始推送：进来的每一条都留档

打开「调试 → 抓取原始推送」后，**打到 `/gw/jjy-hook` 的每一条都会留一份原文**，
包括四类原本会被静默丢掉的：未启用 / 请求体不是 JSON / 白名单拒绝 / `event_id` 重复
（面板上标「已拦截 · <原因>」）。只是"也记一份"，**拦截逻辑本身不动**。

这一条是踩出来的：`ignored` 和 `rejected` 原本只有计数器，看着像"根本没收到推送"，
其实是收到了被挡了 —— 而答案就躺在被丢掉的报文里。同理，每种 `event_type`
第一次出现会把报文打进日志，`GET /gw/status` 的 `jjy.events` 按类型分别计数。

⚠️ 被拒绝的报文是**未经认证的外部输入**（渲染处已做 HTML 转义）。环形缓冲有上限，
最坏情况是被刷屏挤掉真数据 —— 查完记得关。

## 反向代理部署（nginx）

```nginx
# webhook 回调：路径带随机串，不走站点原有的鉴权
location = /hook/<一段随机串> {
    auth_request off;                 # 站点若有 SSO，这行必须加，否则第三方回调会被跳登录页
    proxy_pass http://127.0.0.1:9000/gw/jjy-hook;
    proxy_set_header X-Real-IP $remote_addr;
}

# 工作台：保留站点原有鉴权，只让内部人看（里面是客户对话原文）
location = /workflow { return 301 /workflow/; }
location ^~ /workflow/ {
    proxy_pass http://127.0.0.1:9000/;
    proxy_set_header Host $host;

    proxy_buffering off;              # SSE 必须，否则消息不实时刷新
    proxy_read_timeout 3600s;         # SSE 是长连接，默认 60s 会被掐断
}
```

前端用的是**相对路径**，所以挂在根路径或子路径都能用。
但 `return 301` 不能省 —— 不带尾斜杠访问时相对路径会解析错，页面白屏。

`listen_addr` 默认 `127.0.0.1`，只绑本机，公网唯一入口是反向代理。

## 两套 id（接群/联系人接口前必须先搞清楚）

语聚的**聚合对话**和**企微代运营群管理**是两套 id 体系，长得完全不一样：

| | 聚合对话（webhook / 发送接口） | 企微群管理（群列表 / 联系人列表） |
|---|---|---|
| 会话 | `chat_id` = `5389da0d-…-142889` | `imRoomId` = `R:10942308524386327` |
| 人 | `user_id` = 32 位 hex | `imContactId` = 16 位数字 |

**发送接口只认聚合对话那套。** 拿群列表的 `imRoomId` 去发消息大概率发不出去。

唯一的桥梁在推送报文里：`source_addition.room_id` 就是 `imRoomId`，
`source_addition.bot_wxid` 就是 `imBotId`。所以本程序见到一次就存进
`sessions.room_id` —— 也因此，**只有来过消息的群才映射得上**。选人面板里
映射不上的标成「未来过消息」，但**照样可以选**：它只出现在「指定会话」这个
触发条件里，存的是 `imRoomId` / 人 id 这类恒定身份，第一条消息推过来时
`_match` 拿 `room_id` / `external_contact_id` 就对上了，不需要提前有 `chat_id`。

发消息则相反 —— 动作里已经没有「发到别处」这回事了：「自定义回复」和
「调用接口」的回复都只回**消息来源那个会话**，来源的 `chat_id` 就在推送里，
不存在发不出去的情况。

人的那套同理：选人面板给的是 `imContactId`，消息里带的是 `user_id`，
所以工作流的「指定发送人」两个都比（`workflow.py` 的 `_match`），
靠推送里的 `user_addition.external_contact_id` 对上。

## 「AI 回复」动作

和「调用接口」并列的第三种动作。区别只有一个：**请求体不用你写**，引擎按这个人
和机器人之前聊过的话拼 `messages[]`。

**默认走百炼**（阿里云 DashScope 应用接口），填 `appId` + `apiKey` 就能用：

```
POST https://dashscope.aliyuncs.com/api/v1/apps/{appId}/completion
Authorization: Bearer {apiKey}
{"input":{"messages":[…]},"parameters":{},"debug":{}}
```

取 `output.text`，空了回退 `output.workflow_message.message.content`（应用编排走后者）。
**模型不在这儿配** —— 百炼是在百炼应用里选的。关掉「百炼专用」就是 OpenAI 兼容形态，
默认从 `choices.0.message.content` 取，路径可改。

**「附加参数」是唯一的额外配置口子**：一段 JSON，浅合并进请求体顶层。
特殊的是 `system` 键 —— 它会变成消息列表最前面那条 `{"role":"system"}`，
两种模式都认。想传 `model` / `temperature` / `biz_params` 也都写这儿。

### 上下文存在 `ai_context` 表，不从 `messages` 里捞

两层 id：

```
talk_id  用户维度。群 = "imRoomId_人id"，私聊 = "人id"
         两个都是身份，聚合 chat_id 漂移了它也不变 —— 上下文不会因为漂移断掉
sid      送给模型的那一次会话。按闲置模式下超时就换一个新的（清零重来）；
         按轮数模式下一直沿用，靠滑动窗口控制长度
```

⚠️ 这里的 `sid` 和库里别处的 `session_id` / `sid`（`"R:"+chat_id`，聊天会话的**地址**）
同名不同义。

「上下文怎么带」二选一，**两种模式的行为不只是数字不同**：

| | |
|---|---|
| **按轮数** | **滑动窗口**：带最近 N 轮（一问一答 = 1 轮 = 表里 2 行），最老的一轮一轮掉出去。渐进遗忘，不会聊到一半突然失忆。`sid` 不换 |
| **按闲置** | **硬边界**：距 `sid` **最后一行**超过 N 分钟就换新 `sid` = 清零重来。聊得勤就一直续着 |

这样：

- 群里两个人同时 @ 机器人，**各聊各的**，从 `messages` 表捞是做不到的
- 同一个会话可以挂两条 AI 工作流（一条答技术一条答商务），各记各的
- 只有真喂给模型、以及模型真答过的内容才进来 —— 图片占位符、撤回、
  别人的群聊闲话都不会污染上下文
- 一条工作流挂两个 AI 动作（一个答技术一个答商务）也各记各的：键带动作
  序号，否则第二个会把第一个的回答当成自己说过的话。第 0 个用裸 `wf_id`，
  这样绝大多数（只有一个 AI 动作的）工作流不受这个规则影响

`talk_id` 里两个 `or` 兜底是给**非企微渠道**（抖音/小红书/钉钉）留的，那些推送
既没 `room_id` 也没 `external_contact_id`：

```
人  external_contact_id  优先（实测跨群稳定），没有就退回推送的 user_id
群  imRoomId             没有就退回聊天会话地址
```

不兜的话那类群会全塌成同一个 `talk_id`，A 问的话 B 下一轮就读到了。两个人 id
都拿不到时**整个不碰上下文**，当成一次性问答 —— 宁可没记忆也不能串台。

### 清理：只有按天过期这一道

**超过 7 天的行删掉**，`storage.ai_context_days` 可调（0=不过期）。`ts` 上有索引，
启动扫一次 + 之后每小时一次（搭 `media_gc` 的车）。

不做「每人留 N 行」那种条数裁剪：读取侧本来就只取最近 N 轮（滑动窗口）或当前
`sid`，历史留多少都不影响送给模型的内容，再叠一个上限只是多一条 `DELETE`。
也就是说**这是唯一约束这张表大小的机制，别把它关了**。

`date` 列存 `YYYY-MM-DD` 本地日期，`sqlite3` 里直接能看、也能 `GROUP BY date` 按天统计。

取法两选一，都可自定义：**按条数**（最近 N 条，1–100）或 **按时间**（最近 N 分钟，
1–1440）。读的时候 `session_id IN (siblings)`，`chat_id` 漂移了上下文也不断。
**发出去了才落库** —— 模型答了但没发成不写，否则下一轮会基于一段对方从没看见过的
对话往下编。每份上下文最多留 200 行。

### 「@我」判定：只能拿昵称在正文里找，实测过

**语聚报文里没有任何结构化的 @ 字段。** A/B 实测（2026-08-26，企微代运营群「牛来」）：
同一个群、同一个人、相隔 3.5 秒发的两条（一条 @ 了机器人、一条没 @），
逐字段拍平对比，**键集合完全一致**，只有 5 处不同：

| 字段 | 差异来源 |
|---|---|
| `event_id` | 每次推送不同 |
| `message.message_id` / `message_content.message_id` | 每条消息不同 |
| `message_create_time` | 差 3.5 秒 |
| **`message_content.text`** | **唯一的语义差异** |

`source` / `source_addition` / `user` / `chat` / `channel_num` / `message_type` /
`message_trigger_type` 全部一模一样。没有 `at_list` / `mention` / `is_at` / `remind`。

⚠️ **`rule_id` 也不能用来判 @。** 那条规则名叫「RTE 助手企微调用百炼回复-私聊+群@」，
看着像上游已经筛过，**但没 @ 的那条照样推过来了，`rule_id` 同样是 `1557`** ——
「群@」只是规则的名字，不是生效的过滤条件。

**@ 的正文长这样，注意括号：**

```
"@RTE智能助手(RTE智能助手) 1"
```

不是 `@昵称 正文`，是 **`@昵称(备注名) 正文`**。判定用子串包含没问题，但**剥离**时
只 `replace("@"+昵称)` 会留下 `(RTE智能助手) 1` 这种垃圾。剥的正则见
`_strip_at()`，连可选括号段和尾随空白一起吃掉（企微常用 U+2005 窄空格，
`\s` 覆盖它 —— 类别 Zs）。

**昵称以推送里的为准。** `at_me` 原先用 `config.jjy.bot_name`，那是手配的，
实测配错就静默全挂、还没有任何报错：

| `bot_name` | `at_me` |
|---|---|
| `"RTE智能助手"` ✓ | 1 |
| `""` | 0 |
| `"RTE 智能助手"`（多一个空格） | 0 |
| `"rte智能助手"`（大小写） | 0 |

而**每条推送都带 `source_addition.bot_name`**，是语聚给的权威值，改群昵称也跟着变。
所以 `jjy.py` 里改成**推送优先、配置兜底**（非企微渠道没有 `source_addition`），
生效值存进 `msg["jjy"]["bot_name"]`，下游剥前缀直接读它。

### 「@我」会被锁死

群里靠 @ 决定「这轮对话是谁在问」，所以工作流里一旦有 AI 回复动作，
「是否 @」就被锁成**必须 @** 并置灰（`_norm` 里也兜了一道，改 `workflows.json`
绕不过去）。**私聊不受影响** —— `at_me` 是拿机器人昵称在正文里匹配出来的（`jjy.py`），
私聊压根不参与计算，所以 `_match` 只在群聊校验这个条件。

### 回复默认「引用 + @ 提问的人」，两个开关，**只在群里生效**

私聊是一对一，引用谁、@ 谁都是明摆着的，加了只是噪音，所以两个开关在私聊一律不作用。

@ 是**正文前缀 + 结构化 `mention` 双管齐下**：前缀 `@张兵 ` 保证看得见（语聚推过来的
@ 本来就是正文里的纯文本，`at_me` 就是这么认出来的），`mention` 争取真被 @ 到、有红点。

**`mention` 字段实测**（直接打 `/v1/openapi/aggregate/message/send`，文档里没写这些）：

| `message_content.mention` | 结果 |
|---|---|
| `["1688851163628036"]` — `external_contact_id` 数组 | ✅ `Code 2000` |
| `"1688851163628036"` — 裸字符串 | ❌ 503 `invalid message body`，**必须是数组** |
| `["2919edc…de88"]` — 推送的 `user_id` | ❌ 503 `the mention user(...) is not in the room` |
| `["@all"]` | ❌ 503 同上，**没有这个特殊值** |

那句 `is not in the room` 说明**语聚是拿这个 id 去群成员表里查的** —— 所以它要的必然是
企微那套 id，而且查不到就整条发送失败。正常情况不会踩到（要 @ 的人就是刚在这个群说过话
的人），但人退群、`external_contact_id` 缺失都可能。所以：

- 拿不到 `external_contact_id` 时**不退回 `user_id`**，那是必然失败的一次白往返；
  正文前缀照样加，只是没红点
- `_wf_send` 带 `mention` 发失败时**摘掉它重发一次**，回复不会因为一个 @ 发不出去

⚠️ **引用**只有企微代运营渠道生效，别的渠道语聚直接忽略这个字段 —— 不报错，没效果。

## 图片和文件怎么进工作流

客户发来的截图和日志压缩包，语聚给的是**公开的 S3 直链**（不带签名、无鉴权直接
200、实测不过期），所以工作流不用下载，把 URL 转给下游就行。

「调用接口」动作的请求体里有个 `{attachments}` 变量，直接吐出下游要的形状：

```jsonc
{"question": {"text": "{content_clean_json}", "attachments": {attachments}},
 "session_id": "{talk_id}"}
```

⚠️ **`{attachments}` 是整段 JSON 数组，要放在双引号外面** —— 和 `{xxx_json}`
（放引号内的转义值）刚好相反。无媒体时它是 `[]`，所以同一个模板文本和图片都能用，
不需要两条工作流。

### 一份能直接抄的配置

| 项 | 值 | 为什么 |
|---|---|---|
| 是否@ | **必须@** | 承接窗口只在这个前提下启动 |
| 消息类型 | 随意（**只勾「文本」更严格**） | 承接进来的媒体不受这里限制，见下 |
| @ 承接窗口 | **300** 秒 | 覆盖「传文件 → 组织语言 → 发问」这个连贯动作 |
| 串行执行 | **看下游并发能力**，见「几个对接上的取舍」 | 开了就走不到下游的合并 |
| 提取字段 | `answer` | |
| 超时 | **调大**（默认 10 秒不够） | 下游要先下载附件再跑 CLI |
| 重试次数 | **0** | 409/422 本来就不重试，502 才有意义 |

请求头填 `X-Gateway-Key: <key>`，请求体就是上面那段。

### 三个上限，超了当场剔除

| 项 | 值 | 为什么在本地就拦 |
|---|---|---|
| 单个附件 | 10MB | 下游 `ATTACHMENT_MAX_BYTES` 默认就是这个，超了它回 400 |
| 单次附件数 | 8 | 下游请求模型的固定限制 |
| `question.text` | 20000 字符 | type 12 合并转发展开 50 行能顶穿，超了 422 |

剔除的原因会写进**运行记录**（`… · 主播挂机一晚后不在麦上.zip 超 10MB 未上传`）。
不静默丢 —— 静默的话用户只会看到「模型没看见我的文件」，查不出为什么。

明知必失败就不发，和「拿不到 `external_contact_id` 时不退回 `user_id`」是同一条道理。

### 类型映射：voice 不当附件

`image → "image"`，`file` / `video → "file"`。**语音跳过** —— 语聚已经把语音
转写进正文了（`jjy._as_text` 的 type 3），再传一遍附件是重复。

⚠️ URL 必须用语聚原始那个（`media.cdn.url`）。本项目的 `/media/<id>` 在反代鉴权
后面，下游取不到，而且它明确禁内网地址。

### 群里发图片：@ 承接窗口

企微里**发图片没法同时 @ 人**，而 `at_me` 是拿昵称在正文里找出来的、图片正文是
空串 —— 所以配了「必须@」的工作流，群里的图片永远触发不了。这条路原先是死的。

工作流级的 `attach_window_sec`（默认 300 秒，0=关闭）打开这个口子，**按 `talk_id`
（人）算而不是按会话** —— 群里 A 和 B 各承接各的，不会串台：

| | 行为 |
|---|---|
| **向前承接** | 图片先到 → 暂存不触发。这个人 @ 提问时一并带走，**一次**调用同时拿到问题和附件 |
| **向后承接** | @ 过之后 N 秒内再发的图片，算接着上一句问的，直接触发 |

没 @ 的**纯文本**一律拦住，窗口只对图片/文件开口子 —— 放行的话窗口期内群里任何
闲聊都会触发，那就不是承接是失控了。

**消息类型怎么勾都不影响承接。** `msg_types` 管的是「什么消息**开启**一轮对话」，
承接窗口管的是「什么消息**延续**已经开着的那一轮」—— 两件事，所以被承接进来的
媒体**不受类型过滤**（`_match` 里的 `carried` 标记）。

不分开的话，最自然的那种配法反而会把路堵死：只勾「文本」时，@提问之后补发的
截图会被类型过滤挡下，既不触发也送不出去，只能躺在暂存区等下一次 @，客户等不到
任何反应。现在只勾文本也能走通两个方向，实测（只勾「文本」）：

```
① 先发截图（@之前）  → 暂存
② @提问             → 第1次 text=提问, attachments=1     向前承接
③ @后补日志文件      → 第2次 text='[文件] small.log', att=1  向后承接
④ @后再补一张图      → 第3次 text='', att=1                向后承接
```

### 两种顺序，两条路径

| 客户的操作 | 走哪条路 | 下游收到 |
|---|---|---|
| **先发文件/图，再 @提问** | **本地承接窗口**拼好 | **1 次**，text + attachments 齐全 |
| **先 @提问，再补文件/图** | 两次请求，靠**下游自己的并发替代**合并 | 2 次，第 1 次被替代回 409 |

第一种完全不经过下游的合并机制 —— 承接窗口在发出去之前就拼好了，没有 409、
也没有白跑的 Hermes 进程，是更干净的那条路。

第二种躲不掉：文本到达那一刻它就是一条完整的、该回答的问题，引擎没有理由压着
不发。只能靠下游「后来的请求替代尚未完成的旧请求」把两边并起来。

**承接窗口只在「必须@」+ 群聊时启动**，少一个条件都不合并（实测）：

| 场景 | 先文件后文本 |
|---|---|
| 群聊 · 必须@ | **1 次** ✅ |
| 群聊 · @不限 / 必须未@ | 2 次 |
| 私聊（任何设置） | 2 次 |

`@不限`的群每条消息本来就会触发，没有「被挡下来」的消息需要暂存；私聊压根没有
@ 这道门槛，暂存它等于客户传完文件干等没反应。

私聊那 2 次不算丢东西：两条共用同一个 `session_id`，下游是同一个会话的两轮，
文件还在那个会话的附件目录里。代价是第一轮会先答一句。这也是 session 用**人级
`talk_id`** 而不是会话级 `{source}` 的理由 —— 群里 `{source}` 是所有人共用的，
用它下游会读到别人的对话。

`talk_id` 的格式实测合下游 `session_id` 的正则
`^[A-Za-z0-9][A-Za-z0-9._:-]{0,119}$`（`:` `_` `-` 都在白名单）：

```
群    R:150707549702875_1688851163628036      长度 34
私聊  1688851163628036
```

### 送给模型的正文要剥掉 `@昵称`

用 `{content_clean}` 而不是 `{content}`。两个原因：

1. 下游只有「最终 prompt 不含 `@`」才走纯文本快捷路径，带着 `@昵称` 恒假。
2. **`@` 在 Hermes 里是有语义的** —— 附件就是以 `@file:/tmp/…` 引用的，
   `@RTE智能助手` 很可能被当成一个解析不了的文件引用。

### 回复也能「引用 + @ 提问的人」

「调用接口」和「AI 回复」两个动作都有这两个开关，拼装逻辑共用 `_decorate()`。
**只在群里生效** —— 私聊是一对一，引用谁、@ 谁都是明摆着的，加了只是噪音。

⚠️ 默认值**两个动作不一样**：AI 回复默认开，调用接口默认**关**。后者是通用动作，
线上已有的工作流大多在调普通接口，升级后不该突然开始引用和 @ 人。

### 几个对接上的取舍

- **不传 `user_id`**。下游文档明说续聊别重复传，值和原会话不一致会 409。而
  `talk_id` 优先用 `external_contact_id`、`{sender}` 是推送的 `user_id`，
  **两套 id 空间**，某条推送缺前者就可能不一致。落成 `guest` 无所谓，
  `session_id` 本身是人级的，追溯不丢。
- **`409` / `422` 不重试**（`_request` 的白名单里）。409 是「旧请求被新请求替代」，
  重试等于反过来把新的挤掉，越试越乱；422 是请求体校验失败，重试永远同样结果。
  **`502` 刻意还留着重试** —— 那是下游 CLI 执行失败/超时，属瞬时故障。
- **「串行」开关和下游的合并机制是互斥的，得二选一。** 串行的定义就是「前一条跑完
  才发下一条」，而下游要合并必须两个请求**在时间上重叠**。实测（下游每条处理 6 秒、
  两条消息间隔 2 秒）：

  ```
  串行【开】                        串行【关】
  IN   t= 2.5s  文本进来             IN   t= 2.5s  文本进来
  OUT  t= 8.5s  跑完了               IN   t= 4.5s  图片进来，第一条还在跑 ✅
  IN   t= 8.5s  图片这才发出          OUT  t= 8.5s
  OUT  t=14.5s                      OUT  t=10.5s
  ```

  串行开着，「先 @提问后补图」永远是两次独立回答（客户收到两条回复）；关掉才走得到
  409 合并（客户只收到一条）。

  但**串行防的是另一件事** —— 注释里那句「Codex 代理并发=1」指的是**跨会话**并发：
  群里五个人同时 @ 机器人，五个下游进程一起起来。下游的替代机制只管**同会话**
  （`user_id + session_id` 相同），不同的人是不同 session，是真并发。

  | | 关串行 | 开串行 |
  |---|---|---|
  | 同一个人先文后图 | 能合并，一条回复 | 两条独立回复 |
  | 并发上限 | `WORKER_COUNT`（3）个 | 1 个，**所有人排一条队** |
  | 下游跑 30 秒时，第 5 个提问的人 | 基本不等 | 等 2 分半 |

  **判断点是下游能不能同时跑 3 个**：能就关串行；不能（机器扛不住 / 有全局锁）就
  留着串行，放弃「先文后图」的合并，接受两条回复 —— 信息不丢，只是第一条答得早了点。
  真要收紧并发，调 `WORKER_COUNT` 比开串行更合适：那是并发闸，串行是单线程闸。
- **`timeout_sec` 记得调大**。默认 10 秒，而下游要先下载附件（30 秒超时）再跑
  CLI。上限 1900 秒。
- ⚠️ **鉴权 key 目前明文存在 `workflows.json` 里**，后台也原样回显，不像
  `jjy.api_key` 有打码。填 `X-Gateway-Key` 之前心里有数。

## 数据保留

| 表 | 默认 | 配置 |
|---|---|---|
| `messages` | 每会话 5000 条 | `storage.max_msg_per_session`，0=不限 |
| `workflow_runs` | **全部保留**（前台只往回翻 2000 条） | 裁剪 `storage.max_workflow_runs`（>0 才裁）；前台窗口 `storage.workflow_runs_view` |
| `wf_counters` | 永不删（卡片上的累计数字） | — |
| `ai_context` | 超过 7 天删掉 | `storage.ai_context_days`，0=不过期 |
| `directory` | 只被下一次同步整份替换 | — |

`workflow_runs` 默认不裁是因为**裁剪是全局的、不分工作流** —— 一条高频工作流刷满
上限就会把低频那条的历史挤没，而运行记录正是出问题时唯一的现场。

运行记录页右上角能按工作流筛选（`GET /gw/workflow-runs?wf=<工作流id>`）。

「库里全留」和「前台能翻多少」是两件事：`workflow_runs_view`（默认 2000）只限制
管理页「加载更多」能往回翻到哪，库里的行一条不动。按工作流筛选时窗口按那条工作流
单独算，所以低频工作流的记录不会被高频的挤出可见范围。

## 设计取舍

- **SQLite + WAL 持久化**，重启不丢历史。
- **游标分页**（`before`/`after` + `limit`，Discord 风格），前台按需加载，不做 offset。
- **SSE 实时推送**（`GET /gw/events`），不轮询；断线重连用 `after=<last_seq>` 补差。
- **未读数走显式 `POST /gw/read`**（Chatwoot 收件箱模型），而不是"拉过就算已读"。
- **会话 ID 用 `R:`/`S:` 前缀包住语聚的 `chat_id`**，群聊/私聊一眼可分，
  且能无损还原回原始 id。
